# jww-reader

Jw_cad の JWW ファイルを Python で読み取るライブラリと変換ツール。**読み取り専用。**

Jw_cad を起動せず、外部変形も使わない。ファイルへの書き込みは一切行わない。
パーサ本体は標準ライブラリだけで動く（PDF 出力のみ `reportlab` が必要）。

## なぜ公開しているか

Jw_cad は国内の建設業界で広く使われている。データ形式の資料は
[公式に公開されている](http://www.jwcad.net/jwdatafmt.txt)が、バイトオフセットの
表がなく、資料に載っていない挙動もある。読み取りの実装も C++ / C# / Go / Rust で
いくつか公開されているが、いずれもほとんど知られていない。結果として現場では、
図面の中身を CAD で開いて人が転記するのが普通になっている。

ここを機械で読めるようにし、**実案件を通したときに何が起きるかまで含めて**
公開することは、業界の生産性という共通課題への貢献になると考えている。

コードより価値が高いのは
**[JWW を機械で読むときに踏む罠](#jww-を機械で読むときに踏む罠)** の章だと思う。
仕様書を読んでパーサを書くところまでは誰でも到達できるが、実案件の図面を通すと
必ずそこで止まる。しかも大半が**エラーにならずに間違った値を返す**種類の罠である。

## 対応状況

### 対応クラス

| クラス | 内容 | 状態 |
|---|---|---|
| `CDataSen` | 線分 | 対応 |
| `CDataEnko` | 円・円弧・楕円 | 対応 |
| `CDataMoji` | 文字 | 対応 |
| `CDataSolid` | ソリッド（多角形塗り・円塗り） | 対応 |
| `CDataTen` | 点・実点 | 対応 |
| `CDataSunpou` | 寸法図形 | 対応 |
| `CDataBlock` | ブロック参照 | 対応（配置位置・倍率・回転角・参照番号） |
| `CDataList` | ブロック定義リスト | **未対応** |

未対応クラスに遭遇した場合は `NotImplementedError` を投げる。黙って飛ばさない。

### 対応バージョン

ファイル先頭に入っているデータ形式のバージョン番号。

| バージョン | 状態 |
|---:|---|
| 700 | **確認済み。** Ver7.02 以降のアプリはすべて 700 を書く（実装メモ 1） |
| 230 | **確認済み。** `CData` ヘッダが 13 バイトでヘッダ後半のレイアウトも違う。この場合レイヤ名・ペン設定は取得しない |
| 351〜699 | **未検証。** 351 以上は 700 と同じ経路を通るので読める見込みだが、サンプルで確認していない |
| 230 未満 | **未検証。** サンプル未入手 |

### 未対応

- `CDataList`（ブロック定義）。エンティティリストの**後ろ**に続くため、未対応でも
  走査は完走し、その分が `trailing_bytes` に残るだけで済む
- 2.5D の高さ情報（`m_sFlg & 0x8000`）。確認した範囲では出現件数 0 で、実データで
  検証できていない
- **書き出し**（→ [書き出しについて](#書き出しについて未実装)）

## 動作確認

実案件の図面 **159 本**を通した。図種は構造図（伏図・軸組図・部材リスト図）・
意匠平面図・天井伏図・特記仕様書。作図系統は 5 つで、
**うち 4 系統はレイヤ割当が 1 つも共通していない。**

検算は 2 つ。(1) リストヘッダが宣言する要素数と、実際に順次走査した要素数が一致
すること。(2) 末尾に残るバイト数が説明できること。
**159 本すべてで両方を満たす**（Ver700 が 152 本、Ver230 が 7 本、総要素数 279 万）。

| 項目 | 値 |
|---|---|
| 最大の図面 | 201,196 要素 |
| 要素数が WORD に収まらない図面 | 6 本（実装メモ 11） |
| 末尾残 6 バイト（ブロック定義・画像なし） | 150 本 |
| 末尾残 2 バイト（Ver230） | 7 本 |
| 末尾残がそれ以上 | 2 本（ブロック定義 / 埋め込み画像。実装メモ 12） |

Ver700 の末尾 6 バイトはブロック定義リストの空カウント＋埋め込み画像数。
ブロック定義や埋め込み画像を持つ図面では、その分が `trailing_bytes` として残る
（`CDataList` は未対応）。Ver230 の末尾残は 2 バイトで、旧版は末尾の構成が違うと
見られるが内訳は未確認。

実案件の図面は社内限りのため、このリポジトリには含めていない。手元の図面で
健全性を確認するには `jww.py verify` を使う。宣言数と実読数の一致・末尾残・
罠 3/6/9 の混入件数を出す。

## 使い方

```bash
python3 jww.py info    input.jww     # バージョン・要素数・縮尺・レイヤ名の要約
python3 jww.py verify  input.jww     # 検算（宣言数＝実読数・末尾残・未対応クラス）
python3 jww.py probe   input.jww     # レイヤ割当の調査（作図系統が変わったら最初にこれ）
python3 jww.py svg     input.jww out.svg
python3 jww.py pdf     input.jww out.pdf     # reportlab が必要
python3 jww.py json    input.jww out.json    # 中間表現をそのまま JSON で出す
```

`reportlab` は `pdf` の中で遅延 import している。PDF を使わないなら不要。

```bash
pip install reportlab      # pdf を使う場合のみ
```

ライブラリとして使う場合。

```python
import jwwread
ir = jwwread.read('input.jww')
```

**新しい作図者の図面に初めて通すときは、必ず `probe` を先に走らせること。**
レイヤ割当は作図者ごとに違い、前の図面の前提はそのままでは通らない（罠 1）。

`jwwutil` は罠に対する前処理をまとめたもの。中間表現の辞書だけを扱う。

| 関数 | 対応する罠 |
|---|---|
| `dedupe(ents)` | 3 幾何的に完全一致する要素を落とす |
| `overlapping_texts(ents)` | 6 同一座標に内容の違う文字が重なっている箇所を返す |
| `is_setting_text(e)` / `drop_setting_texts(ents)` | 9 Jw_cad 自身が書き込んだ設定文字を落とす |
| `normalize(s)` | 8 全角/半角の掛け算記号と数字を揃える |

```python
import jwwread, jwwutil
ir = jwwread.read('input.jww')
ents = jwwutil.drop_setting_texts(jwwutil.dedupe(ir['entities']))
for k, group in jwwutil.overlapping_texts(ents):
    ...   # 人間に見せる
```

## 返り値

`jwwread.read(path)` は辞書を返す。

```python
{
  'version': 700,
  'zumen': 3,                 # 0-4 = A0-A4
  'memo': '...',
  'layers': {(glayer, layer): 'レイヤ名', ...},   # 名前が空のものは除いてある
  'glayers': ['レイヤグループ名', ...],
  'pen_color': {0: ..., ...},
  'pen_width': {0: ..., ...},
  'declared': 32060,          # ファイルが宣言する要素数
  'scale': {0: 200.0, ...},   # レイヤグループ別の公称縮尺の分母
  'entities': [ {...}, ... ],
  'trailing_bytes': 6,
  'schema': 700,              # MFC のスキーマ番号。version とは別物（実装メモ1）
  'header_extra': 0           # ヘッダ終端の想定との差。0 以外なら未知の構成
}
```

Ver230 では `layers` / `glayers` / `pen_color` / `pen_width` は空になる
（ヘッダ後半のレイアウトが不明なため取得していない）。

**座標は「図面上の mm」で入っている。** 実寸に直すには、その要素が属する
レイヤグループの縮尺を掛ける。

```python
実寸mm = 値 × ir['scale'][e['glayer']]
```

図上 `161.5000000000` × 200 = `32300.000000` mm。図面の寸法記入と誤差なく一致する。
レイヤグループごとに縮尺が違う（1/200 の配置図と 1/50 の詳細図が同居する）ので、
**全要素を同じ係数で換算してはいけない。**
ただし公称縮尺そのものが当てにならない図面がある（罠 2）。

エンティティは以下の形。

```python
{'kind':'CDataSen',  'x1':..,'y1':..,'x2':..,'y2':..,
 'layer':..,'glayer':..,'color':..,'style':..,'flg':..,'group':..}

{'kind':'CDataEnko', 'cx':..,'cy':..,'rad':..,'a0':..,
 'asweep':..,'tilt':..,'flat':..,'full':..}

{'kind':'CDataMoji', 'x1':..,'y1':..,'x2':..,'y2':..,
 'shu':..,'sx':..,'sy':..,'pitch':..,'angle':..,
 'font':'...','text':'...','sunpou_flg':..}

# 多角形ソリッド（3点の場合は P3 == P4 になる）
{'kind':'CDataSolid', 'circle':False,
 'x1':..,'y1':..,'x2':..,'y2':..,'x3':..,'y3':..,'x4':..,'y4':..,
 'rgb':..}                      # rgb は線色番号10のときのみ

# 円ソリッド（塗り円・塗り円弧）
{'kind':'CDataSolid', 'circle':True,
 'cx':..,'cy':..,'rad':..,'flat':..,'tilt':..,'a0':..,'asweep':..,
 'ctype':..,'full':..}

{'kind':'CDataTen',  'x1':..,'y1':..,'kariten':..,
 'code':..,'angle':..,'scale':..}   # 後ろ3つは線種100のときのみ

{'kind':'CDataSunpou', 'x1':..,'y1':..,'x2':..,'y2':..,'text':'...',
 'sen':{...},'moji':{...},
 'sxf':..,'senho':[{...},{...}],'ten':[..],'tenho':[..]}  # Ver4.20以降

{'kind':'CDataBlock', 'x1':..,'y1':..,'sx':..,'sy':..,'angle':..,
 'list_no':..}                  # list_no = 参照するブロック定義の番号
```

`CDataSunpou` の `x1..y2` は寸法線の座標を昇格させたもの。
全エンティティが座標を持つという前提で下流を書けるようにしてある。

# JWW を機械で読むときに踏む罠

**この章はパーサの仕様ではなく、利用者への警告である。**
実案件 159 本・作図系統 5 つで実際に踏んだもの。作図系統は A〜E で匿名化してある。

パーサが正しく動いていても、これらは**エラーにならずに間違った値を返す。**
要素数と末尾バイトの検算は通り抜ける。

## 1. レイヤ/レイヤグループの割当に標準は無い

**症状**: 別の作図者の図面に通すと、通り芯が 0 本になる、壁が拾えない、
意匠図の下敷きを構造部材として数える。エラーは出ない。

**原因**: JWW のレイヤ番号に業界標準は無い。159 本の 5 系統で、レイヤの使い方は
こうだった。共通点が無い。

| 系統 | 部材の分け方 |
|---|---|
| A | 伏図本体が 1 つのレイヤグループに収まり、レイヤ名が部材の意味を持つ（通り芯・柱壁・梁・壁・符号文字…）。ただし別のレイヤグループに**意匠図の下敷き**が入っており、必ず除外が要る |
| B | 伏図本体が A とは別のレイヤグループ。**通り芯の「線」と「符号」が別のレイヤグループにある**（同じだと思って片方だけ見ると通り芯が空になる） |
| C | Archicad 出力。レイヤ名は部材名になっているが、**壁・梁・スラブ・基礎・通り芯・ラベルがそれぞれ別のレイヤグループに散る。** 壁は X 方向と Y 方向で別レイヤ |
| D | DXF→JWW 変換。**レイヤが 2 つしか無く、レイヤでは部材を分けられない。線色が部材を持つ。** しかも同じ色でも図によって役割が変わる（基礎伏図の色 2 は基礎梁、階の伏図の色 2 は壁） |
| E | 意匠図（Archicad 出力）。**レイヤ名が全て同一の文字列で意味を持たない。** レイヤの意味は平行線の離れの分布から推定するしかない |

**対処**:

- **レイヤ番号を定数で書かない。** 作図系統ごとのプロファイルを外部データ
  （辞書・JSON・環境変数）に出す。これをやらないと 2 系統目で作り直しになる
- プロファイルのキーを**レイヤ番号に限定しない。** D は線色、E は幾何が意味を持つ
- 新しい図面はまず割当を調べる工程を挟む（`jww.py probe`）。
  レイヤ名・公称縮尺・`(glayer, layer)` ごとの要素数と座標範囲・図題らしい文字を出す

## 2. 公称縮尺と実寸が食い違う図面がある

**症状**: 縮尺どおり換算した寸法が、図面に書かれた寸法と合わない。

**原因**: レイヤグループには公称の縮尺が入っていて `ir['scale'][glayer]` で読めるが、
**作図者が別の縮尺で描いた図形をそのレイヤグループに置いていることがある。**
実例では、通り芯が公称 1/100 のレイヤグループにあるのに、実寸は伏図本体の 1/150 で
合った。

**対処**: **寸法文字で検算する。** 通り芯スパンなど値が分かっている寸法を 1 つ選び、
`座標差 × 縮尺` がその値（例: 5,700 / 7,400）になるか確かめる。合わなければ
プロファイル側で縮尺を明示して公称値を上書きする。**公称縮尺は当てにならない。**

## 3. 同じ要素が同じ座標に二重に入っている

**症状**: 「作図ミスの多い図面」に見える。通り芯ラベルが全て重複しているように
見え、重複を除く処理に全部かかって**通り芯が 1 本も取れなくなる。**
壁の本数が倍に数えられ、延長や面積が倍に出る。

**原因**: 2 つある。

- **Archicad から出力した JWW は、文字も線も系統的に二重に書く。** 図面としては
  見た目が変わらないので、Jw_cad で開いても気づけない
- それ以外の作図系統でも重ね書きは起きる（修正時の描き直し、コピー貼り付け）。
  実測 159 本のうち **135 本**に完全一致の重複があった。総要素 279 万のうち
  9.5 万件（3.4%）。系統的に二重書きする図面では**同一図面の 59%** が重複だった

**対処**: 読み込み直後に**幾何的に完全一致する要素を落とす前処理を入れる。**
`jwwutil.dedupe()` として同梱してある。

**ここで踏む二次的な罠**: 座標フィールドはクラスごとに違う。
**円弧（`CDataEnko`）は `x1/y1` を持たず `cx/cy/rad` で表される。**
`x1,y1,x2,y2` だけで同一性のキーを作ると、**同一レイヤの円弧が全部 1 つに潰れて
大量の要素が静かに消える。** これを実際にやってしまい、重複率が 60% に見えていた
（正しくは 3.4%）。`jwwutil.dedupe()` は中間表現の数値・文字フィールドを全部
たどることでこれを避けている。曲線属性グループ番号と属性フラグは、
二重書きの片方だけ値が違うことがあるためキーに含めていない。

落とすかどうかは用途による。**図面をそのまま描き直すなら落とす必要はない。
数を数える用途（本数・延長・面積）では落とさないと倍に出る。**

**罠 6 とは別物**で、こちらは内容まで一致するものだけを落とす。

## 4. 1 つのファイルに複数の面が入る

**症状**: 1 階と 2 階の部材が混ざる。

**原因**: 図面 1 枚に 1 階伏図と 2 階伏図の両方が入っている、という作り方が普通に
ある。**分け方が系統ごとに違う。**

- 系統 A: **x 方向**に並ぶ。通り芯符号の x クラスタで切れる
- 系統 C: **y 方向**に積まれる（下に 1 階、上に 2 階）。x クラスタで切ると 1 面に
  見えてしまう。図題文字の y 座標で切る必要がある
- 系統 B: 1 ファイル 1 面（階ごとにファイルが分かれている）

さらに、**用紙外に別図面が置き捨てられていることがある。** 部材リストの図面に、
用紙の下（y が大きく負の領域）に伏図が丸ごと残っていた例があった。座標範囲で
切らないと別図面の文字を拾う。

**対処**: 図題文字（「○階伏図」「○リスト」等）の位置を先に拾い、
面の分け方を図面ごとに判定する。**1 ファイル 1 面と決め打たない。**

## 5. 表（部材リスト）は行を連結すると列がずれる

**症状**: G4 の断面が G11 の欄に入る。**エラーにならない。**

**原因**: 列方向レイアウトの表（1 列＝1 部材符号、行＝項目）で、
**その階に存在しない符号はセルが空ではなく、文字要素そのものが存在しない。**
JWW に入っているのは座標付きの文字であって表ではないので、「空セル」という概念が
無い。行ごとに文字を x 順に連結すると、符号の列数と数値の列数が合わず、右にずれる。

**対処**: **必ず x 座標で列に割り当てる。** 符号行の x 座標を列アンカーとして確定
し、以降の各行の文字を最も近いアンカーに配属する。連結は使わない。

付随して踏むもの:

- 符号行の右側に「共通事項」の注記文字が同じ高さで置かれている。
  **符号らしい文字列（英字＋数字）だけをアンカーに採る**
- 断面寸法（壁厚・梁せい）はラベル付きの行ではないことがある。「厚」という
  ラベルを持つ行ではなく、**符号列の下に並ぶ数値だけの行**として描かれている
- レイヤグループの 1 つが図面枠（縮尺 1/1）になっている。除外する
- 1 枚に表が複数入る（地中梁・壁・スラブ・片持ちの 4 表が四分割）。
  座標の窓で 1 表ずつ処理する

## 6. 消し忘れの文字が別の文字の真上に重なっている

**症状**: 同じ座標に違う文字が 2 つある。罠 3 の重複除去では落ちない（内容が違う）。

**原因**: 作図時の修正で、古い文字を消さずに新しい文字を上に書いている。
Jw_cad の画面では後から描いた方が上に重なるので、人間には見えない。

**対処**: 同一座標に複数の文字要素があることを検出し、**人間に回す。**
どちらが正しいかは機械には決められない。黙って片方を採ると、間違いが検算を
通り抜けて最後まで残る。

## 7. 図面側に作図ミスがある前提で書く

**症状**: 通り芯符号が重複している。符号が部材から離れすぎている。

**原因**: 図面は人が描いたもので、CAD は整合性を検査しない。

**対処**: **異常を例外で落とさず、「人間に回す」出口を作る。**

例として、柱符号は柱の左右どちらかにオフセットして置かれ、通り芯の交点から
数百 mm ずれる（800 角の柱で 760〜1,090 mm）。最近傍の交点に丸めるのが妥当だが、
**最小スパンの半分を超えるずれは丸めずに保留にする。** 閾値を持たずに最近傍へ
丸めると、隣の交点に付いた符号が静かに間違った位置に入る。

通り芯レイヤには寸法の補助線が混ざっていることもある。長さで芯を選ぶと補助線を
拾うので、**通り芯符号の座標に一致する線だけを採る。**

## 8. 掛け算記号は全角と半角が揺れる

**症状**: `300x1800` で検索しても `300×1800` が引っかからない。

**原因**: 断面表記の掛け算記号に `x`（半角エックス）・`ｘ`（全角エックス）・
`×`（全角の乗算記号 U+00D7）が混在する。同じ図面の中でも揺れる。数字にも全角が
混じる。

**対処**: 文字を取り出したら正規化する。`jwwutil.normalize()` として同梱してある。

```python
import unicodedata
def normalize(s):
    s = unicodedata.normalize('NFKC', s)       # 全角数字・全角ｘ → 半角
    return s.replace('×', 'x').replace('X', 'x')
```

NFKC は全角英数を半角にするが、`×`（U+00D7）は変換しないので個別に置換する。

## 9. Jw_cad 自身が設定を文字要素として図面に書き込んでいる

**症状**: 文字を総ざらいして符号や注記を集めると、図面に存在しない文字列が混ざる。

**原因**: Jw_cad は印刷・表示の設定を、`Printer_PaperSize = 0` のような
**普通の文字要素**として図面の中に書き込む。実測で現れたキーは
`Printer_*` / `Draw_*` / `View_*`。

厄介なのは置かれる場所で、**図面枠のレイヤグループに入るとは限らない。**
実測 159 本のうち **50 本**に混入しており、`(15,15)` や `(15,0)` のような
図面枠側だけでなく、`(0,0)` のように部材が載っているレイヤにも入っていた。
レイヤで除外しようとしても取りきれない。

**対処**: 文字列の形で判定して落とす。`jwwutil.drop_setting_texts()` として
同梱してある。座標も図面の外にあるとは限らないので、座標で切るのも当てにならない。

# 実装メモ

ここからはパーサを書く人向け。公式のデータ形式資料は公開されている。

http://www.jwcad.net/jwdatafmt.txt

全エンティティの `Serialize()` 関数がソースコードのまま載っている。
ただしバイトオフセットの表はないので、自分で積算する必要がある。

以下は、その資料だけでは実装できなかった点。

## 1. バージョン番号は 700 で止まっている

`JW_DATA_VERSION` は Ver8 でも Ver10 でも 700。
アプリの版ではなくデータ形式の版であり、7.02 以降は動いていない。

したがってバージョン番号（ファイル先頭）だけで機能の有無を判定する設計にしてはいけない。
クラス名とレコード長で見る。

**MFC のスキーマ番号もバージョン番号とは別物。** クラス登録
（`0xFFFF` + スキーマ番号 + 名前長 + クラス名）に入っているスキーマ番号は、
実測ではデータ形式版 700 のファイルのあいだでも値が違った（159 本のうち
78 本が `1`、74 本が `700`、Ver230 の 7 本が `230`）。
**スキーマ番号を照合条件に使ってはいけない。** ここに `schema == version` を
仮定した判定を入れて、半分のファイルが読めなくなった。

## 2. MFC の番号表はクラスとオブジェクトで共有されている

JWW は MFC の `CArchive` シリアライズ。タグは以下（MFC TN002）。

- `0xFFFF` + schema(WORD) + namelen(WORD) + クラス名 … クラス初出
- `0x8000 | index` … 既出クラスの参照

この `index` は**クラスとオブジェクトが同じ番号表を共有し、どちらも
1 つずつ消費する**。実測値の例:

```
CDataSen   = 1
CDataEnko  = 28189   (= 1 + 線分 28187 件 + 1)
CDataMoji  = 30964   (= 28189 + 円弧 2774 件 + 1)
```

クラス番号は 1, 2, 3 と続くだろうと決め打つと、2 つ目のクラスで必ず落ちる。
オブジェクトを読んだあとに番号を進めるのを忘れないこと。

## 3. 資料に誤記がある

`CDataSen::Serialize` は `m_start.x` を 2 回書いている。

```cpp
ar << (double)m_start.x << (double)m_start.x    // ← 2 番目は m_start.y
   << (double)m_end.x   << (double)m_end.y;
```

実データは正しく double×4（始点 x, y → 終点 x, y）。転記ミスと判断した。

## 4. CData 共通ヘッダは 15 バイト、ただし Ver3.51 未満は 13 バイト

```
DWORD m_lGroup      曲線属性グループ番号   4
BYTE  m_nPenStyle   線種番号               1
WORD  m_nPenColor   線色番号               2
WORD  m_nPenWidth   線幅                   2
WORD  m_nLayer      レイヤ番号             2
WORD  m_nGLayer     レイヤグループ番号     2
WORD  m_sFlg        属性フラグ             2   ← Ver3.51 未満は存在しない
                                        ---- 15
```

古い図面が混在するアーカイブでは、ここを分岐しないと以降のエンティティが
2 バイトずつずれて全て崩れる。**入れ子メンバ（`CDataSunpou` の中の線・文字・点）
にも同じ分岐が必要。**

Ver3.51 未満（実測 Ver230）では、さらに 2 つ違う。

- 要素数が MFC の `0xFFFF` エスケープ＋DWORD で書かれる。**件数によらず常に**
  エスケープする（1,262 件でもエスケープする）。→ 実装メモ 11
- ヘッダ**後半**（レイヤ名・ペン設定以降）のレイアウトが違う

後半は仕様が分からないので決め打ちせず、`_find_entity_list()` で
「`0xFFFF` + スキーマ番号(WORD) + 名前長(WORD) + `"CData…"`」の並びを走査して
エンティティリストの先頭を確定している（スキーマ番号は照合に使わない。
実装メモ 1）。縮尺ブロックはヘッダ前半にあり旧版でも同じ位置なので、そこまでは
従来どおり読める。この経路ではレイヤ名・ペン設定を取得しない。

## 5. CDataMoji は線幅の欄に別の値を載せている

資料のとおり、`m_nPenWidth` に「寸法値設定フラグ」が入る。
線幅として解釈してはいけない。

本体レイアウト（実測で確認）:

```
double x1, y1, x2, y2       32
DWORD  文字種                4
double sizeX, sizeY          16
double 間隔                   8
double 角度                   8
CString フォント名           可変（長さ 1 byte + 本体）
CString 本文                 可変
```

## 6. 拡張子は信用しない

`.jww` なのに中身が旧 JWC 形式のファイルが実在する。
先頭 8 バイトが `JwwData.` かどうかで判定する。

## 7. 通り芯は範囲を歪める

通り芯は意図的に長く伸ばされることがある。全要素の最小最大で
バウンディングボックスを取ると図面が極端に小さくなる。
`topdf.py` では上下 0.2% を除外している。

## 8. 要素が 32,766 を超えるとタグが WORD から DWORD に変わる

MFC の番号表（上記 2）の index が `0x7FFE` を超えると、WORD タグが
`0x7FFF` に切り替わり、**実番号は続く DWORD に入る**（クラス参照は
`0x80000000` が立つ）。

```
WORD  0xFFFF          … クラス初出（従来）
WORD  0x8000 | index  … 既出クラスの参照（従来）
WORD  0x7FFF + DWORD  … 番号が大きい場合。実番号は DWORD 側
```

3 万要素程度の図面は境界の直下に収まってしまうため、ここを踏まないまま
「動いている」ように見えることがある。**要素数が 3 万を超える図面で
初めて `KeyError` として現れる。**

## 9. 線種番号 101 以上のソリッドは多角形ではない

`CDataSolid` は通常 4 点の多角形だが、**線種番号が 101 以上のときは
「円ソリッド」（塗り円・塗り円弧）**で、4 点のスロットに頂点ではなく
円弧パラメータが入る。資料の対応は以下。

```
m_start      円心
m_end.x      半径
m_end.y      扁平率
m_DPoint2.x  傾き角
m_DPoint2.y  開始角
m_DPoint3.x  弧長角
m_DPoint3.y  円弧種別（実測では -1 / 5 / 0 のみ出現。-1 が全円と見られる）
```

これを多角形として描くと、パラメータ値が原点付近の座標として解釈され、
**図面全体に巨大な三角形が放射状に走る。** 要素数・末尾バイトの検算は
通ってしまうので、出力を目で見るまで気づけない。

`CDataTen` の線種 100 と同じく、**100 番台の線種番号が拡張形の合図**に
なっている。

## 10. 寸法が CDataSunpou で入っている前提を置かない

Jw_cad の寸法コマンドは、既定では線と文字を別々の要素として出力する。
「寸法図形にする」設定を有効にしたときだけ `CDataSunpou` になる。
作図者の設定次第なので、寸法値を拾うときは `CDataMoji` 側も見る必要がある。

## 11. 要素数が 65,535 を超えるとフィールドが 2 バイトから 6 バイトに変わる

エンティティリストの先頭にある要素数は WORD だが、**WORD に収まらないときは
MFC の `0xFFFF` エスケープになり、続く DWORD に実数が入る**（合計 6 バイト）。

```
WORD  要素数                 … 65,535 以下（従来）
WORD  0xFFFF + DWORD 要素数  … 65,535 超
```

これを知らずに WORD で決め打つと、**エンティティリストの先頭が 4 バイトずれ、
1 件目のクラスタグの読み取りで `KeyError` として現れる。** 1 件も読めないので
「ヘッダの解析を間違えた」と誤診しやすい。実測 159 本のうち 6 本が該当し、
WORD で書かれた最大は 64,108 要素だった。

さらに **Ver230 は件数によらず常にエスケープする**（1,262 要素でもエスケープする）。
件数から形式を推定してはいけない。`0xFFFF` かどうかを見て分岐する。

上記 8 の「32,766 を超えるとタグが DWORD に変わる」とは**別の閾値**であることに
注意する。3 万要素で 8 を踏み、6 万要素で 11 を踏む。

なお本実装は、この 2 バイト／6 バイトの違いに加えてヘッダ末尾の解釈違いにも
耐えるように、エンティティリストの先頭を**クラス登録の並びから走査して確定**して
いる。想定終端との差は `header_extra` として返す（0 でなければ未知のヘッダ構成）。

## 12. 埋め込み画像はファイル末尾に付く

Jw_cad の画像挿入は、**本文が `^@BM<ファイルパス>,<倍率>,<角度>,…` の文字要素**
として入り、**画像データ本体はエンティティリストより後ろ**に置かれる。

したがって画像を含む図面では `trailing_bytes` が画像のサイズだけ増える
（実測で 2 MB を超えた例がある）。末尾残の大きさで健全性を判定する実装は、
ここを例外にしないと画像入りの図面を全部異常と判定する。

画像パスは作図時の絶対パスがそのまま残る。**社外に出す成果物にこの文字要素を
そのまま含めないよう注意すること**（フォルダ構成が漏れる）。

# 書き出しについて（未実装）

現状は読み取り専用で、JWW を書き出す機能は無い。ただし「仕様が非公開だから
原理的に不可能」ではないので、方針だけ記す。

このパーサはヘッダを**意味を読まずに相対オフセットで飛ばしている。**
したがってゼロから JWW を組み立てることは今の知識ではできない。
現実的な道は 1 つある。

**テンプレート差し替え方式**: 既存の JWW を読み、ヘッダ部分をバイト列として
そのまま複写し、エンティティリストだけを差し替える。ヘッダの各フィールドの意味を
知る必要がない。必要になるのは、

1. エンティティリスト先頭のオフセット（Ver230 では `_find_entity_list()` が
   既に求めている）
2. MFC 番号表の管理（クラス初出／既出参照／`0x7FFF` エスケープ）。読み取り側で
   解明済み
3. 末尾の `CDataList` 空カウントと埋め込み画像数

用途として価値が高いのは「ゼロから作図」ではなく**注記の追記**
（算出結果や指摘を図面に書き戻す）で、これなら既存のエンティティ列の末尾に
`CDataMoji` / `CDataSolid` を足すだけで足りる。検証は
`read → write → read` の往復で中間表現が一致することと、
**Jw_cad で開けるかを人が確認すること**の 2 段になる。

実装していない理由は 3 つ。

1. 壊れたファイルを生む可能性があり、検証には人が Jw_cad で開く工程が必須。
   自動テストで担保できない
2. 「ファイルへの書き込みは一切行わない」という現在の性質が、このツールを
   他人が試すときの安全性の根拠になっている
3. 読み取りだけで用途が足りている

実装する場合は**別モジュール・別コマンドに分離**し、読み取り専用でなくなった
ことを明示すべきと考えている。

# 3D 化・IFC 出力について

未実装。ただし「JWW には高さがないので原理的に無理」という整理は**図面次第で
変わる。**

Jw_cad の 2.5D 機能（`m_sFlg & 0x8000` の高さラベル）は、確認した範囲では
出現件数 0 だった。そこからは取れない。取れるとすれば以下の経路で、いずれも
**図面の作り方に依存する。** 断定できるのは「読み取れた」ことまでで、汎用の
手順ではない。

- **壁の厚さ**: ある系統では壁が `CDataSolid` の細長い矩形で描かれており、
  短辺がそのまま壁厚（実寸 150 / 200 mm）になっていた。同じレイヤに
  「壁」「簡易壁」という文字要素が置かれていて、それが唯一の意味づけだった
- **柱**: 同じ図面で 500 mm 角の正方形ソリッドとして拾えた
- **階高**: 断面図が**別のレイヤグループ（別縮尺）として同一ファイルに同居**
  していた。そこの寸法文字から階高・GL・最高高さが読める

つまり必要なのはエンティティ型ではなく、**レイヤ構成と注記文字の読み解き**。
作図者が変わればこの前提は崩れる（罠 1）。自動化する場合は、図面ごとに
「どのレイヤグループが何か」を最初に確認する工程を必ず挟むこと。
